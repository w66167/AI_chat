# 学生手册知识库（知识抽取与入库）

把《杭州电子科技大学学生手册》（2017年9月版，206页，28篇校级/国家级文件）转成可检索、可审核、可追溯的知识库。

本目录解决的是《校园智能客服与知识问答系统需求分析说明书》里最费人力也最容易翻车的一环：**知识资产**。代码只负责把 PDF 变成结构化语料，答案质量和口径正确性仍然需要知识维护人员与审核员把关。

## 目录结构

```text
knowledge_base/
  scripts/
    parse_handbook.py        PDF → 分页文本 → 文档/章/节/条切块（零第三方依赖）
    check_kb.py              校验问答条目的出处可定位、字段完整、页码一致
    export_miniprogram.py    导出小程序可直接 require 的 handbook.js
    build_eval_set.py        生成 150 条评测问题集（题目表可读可改）
    check_eval_set.py        校验问题集：命中目标存在、必含词在原文中、题型与期望匹配
    score_eval.py            打分：关键词基线自测，或对真实系统输出评分
  data/
    handbook_pages.json      206 页清洗后文本（含页脚页码）
    handbook_fulltext.txt    带页码标记的全文，供人工校对
    handbook_docs.json       28 篇文件清单：起止页、章数、条数、字数
    handbook_chunks.jsonl    586 个 RAG 切块（文档/章/节/条/页码/原文）
    handbook_qa.json         30 条问答条目（含出处与审核状态）
    handbook.js              handbook_qa.json 的小程序版本
    eval_questions.json      150 条评测问题（含命中目标、期望行为、必含词）
```

## 复现

```powershell
$py = "C:\Users\zaaaaaaaaaas\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"

# 1. 解析 PDF，生成分页文本与切块语料
& $py scripts\parse_handbook.py --pdf "C:\Users\zaaaaaaaaaas\Downloads\学生手册.pdf" --out data

# 2. 校验问答条目能否追回原文
& $py scripts\check_kb.py

# 3. 导出小程序模块（加 --publish 则把条目置为已发布，仅用于演示）
& $py scripts\export_miniprogram.py

# 4. 生成并校验评测问题集
& $py scripts\build_eval_set.py
& $py scripts\check_eval_set.py

# 5. 跑关键词基线，确认题库可解
& $py scripts\score_eval.py --baseline
```

## 这份 PDF 的坑（都能复现）

1. **文本层是 OCR 出来的，而且按字形片段排布**。直接读文本层得到的是「第一行尾 + 第二行首」交错乱码。脚本用字形坐标重排：同一视觉行的片段按 x 排序，y 抖动 ≤2pt 视为同行。这样做才对上「第一章 总则 / 第一条 为规范……」的语序。
2. **固定的字形替换错误**：`渊/冤` = `（/）`、`尧` = `、`、`咱` = `[`、文号里的 `暂/页/也` = `]/[/[`。注意这些替换必须带上下文——`暂` 在正文里是常用字（暂缓注册、暂行规定），全局替换会把「暂缓注册」改成「]缓注册」。脚本只在数字之间做替换。
3. **同名不同体的编号**。有的文件按「第X条」编排，有的直接「一、」「（一）」。先判断该文件是否含「第X条」，再决定切块边界，否则整篇文件切不出块（医疗相关规定最初就是 0 块）。
4. **假条标题**。「第二条所列情况者，授予……」这种跨行衔接语形似条标题，必须排除，否则同一条会被切成两半、页码定位也会错。
5. **表格页单独剔除**（123—126 创新学分一览表、136—137 奖学金金额表、186—187 保险赔付表、197—205 社团附件表）。这些页现在是纯文本丢了表格结构，需要人工整理成结构化字段后再入库。

## 30 条问答条目

分类分布：学籍管理 6、成绩与考试 6、学籍异动 4、毕业与学位 3、纪律与申诉 3、奖助与资助 4、校园生活 4。

每条包含：标题、同义问法（≥2 条，供检索匹配）、答案、办理步骤、咨询渠道、出处（文件+条+页码）、适用范围、版本、审核状态、`handbook_ref`（机器可读的出处）。

`check_kb.py` 会验证三件事，全部通过：
- 每条 `handbook_ref` 都能在 586 个切块里唯一定位到某条，且页码落在该条的页码范围里；
- `source` 字符串里写的页码与 `handbook_ref.page` 一致；
- 答案与出处原文有足够字符级重合（防止张冠李戴）。

**全部条目的状态都是 `draft`，这是有意的。** 原因有三个：
1. 手册是 2017 年版，部分条款（如奖学金金额、医保结算比例、勤工助学 15 元/小时）大概率已被后续文件调整；
2. 手册前言明确「本手册内容与学校文件不符的，以学校文件为准」，最终口径要对着现行文件核；
3. 手册里只有条款，没有办理窗口、联系电话、办公时段，而需求文档 FR-21 要求答案必须带这些信息——这部分只能人工补充。

审核流程：维护人员按 `handbook_fulltext.txt` 对应页核对 → 修改 `status` 为 `pending` → 审核员核对后置 `published` → 重新运行 `export_miniprogram.py`。

## 接进当前小程序

`handbook.js` 与 `miniprogram/data/knowledge.js` 的字段兼容（`id/category/title/aliases/answer/steps/channel/source/scope/version/updatedAt/status`），只多一个 `handbookRef`。

改 `miniprogram/data/knowledge.js` 末尾两行即可合并：

```js
const handbook = require('./handbook');
const knowledge = [...definitions.map(toItem), ...handbook.knowledge];
const categories = ['全部', ...handbook.categories];
```

注意 `store.js` 的 `getKnowledge()` 只返回 `status === 'published'`，所以合并后默认**不会**出现在问答里——这正是需求文档要求的「审核后生效」。演示时可用 `export_miniprogram.py --publish` 生成全发布版本，但要明确标注为演示数据。

首页「已发布知识数量」、问答页来源展示、知识工作台的「创建修订草稿」都能直接复用，因为字段是对齐的。

## 评测问题集（150 条）

`eval_questions.json` 对应需求文档验收第 1 条的第一批题目（同结构继续追加到 300 条即可）。

| 题型 | 条数 | 期望行为 | 考什么 |
| --- | --- | --- | --- |
| 标准问 | 45 | `answer` | 问法与条文接近时的基本命中 |
| 同义问法 | 42 | `answer` | 口语化改写（“两门考试撞了”“挂科了还能补考吗”） |
| 多轮追问 | 20 | `answer` | 承接上一轮省略主语/条件，含跨条承接（GPA→学位、警示→退学） |
| 澄清 | 12 | `clarify` | 只给话题词（“宿舍”“奖学金”）时不得瞎猜一条 |
| 无答案 | 20 | `refuse_noanswer` | 手册确实没有的内容（图书馆、校园卡、校车、快递） |
| 边界／越权 | 8 | `refuse_boundary` | 代报修、代提交、查个人成绩、投诉转办、催办 |
| 冲突／时效 | 3 | `answer_with_caveat` | 2017 年版条款是否仍然有效、与上位规定冲突 |

每条字段：

```json
{
  "id": "ev-001", "type": "standard",
  "question": "新生不能按期到校报到应当怎么处理？",
  "gold": ["hb-123"],            // Top-3 命中判定用，空表示不该命中任何已发布知识
  "expect": "answer",            // 期望行为
  "must_include": ["两周"],       // 回答必须出现；同时校验它确实在 gold 原文里
  "must_not": [],                // 出现即判错（编造的电话、承诺性表述）
  "difficulty": 1, "note": "学籍规定第三条…"
}
```

覆盖：命中目标 78 个不同切块、22 篇手册文件；学籍类占 31 条（手册本身以学籍管理篇幅最大），住宿 9、处分 7、申诉 6、转专业 5。

### 校验与打分

`check_eval_set.py` 全部通过（0 错误 0 警告）：条数、题型分布、`gold` 存在性、`must_include` 是否真在命中块原文中、题型与期望行为是否匹配、有无重复题、多轮题是否带上下文。

`score_eval.py` 支持两种模式：

```powershell
# 关键词基线自测（不需要任何外部服务）
& $py scripts\score_eval.py --baseline

# 对真实系统打分：把系统输出写成 predictions.json
& $py scripts\score_eval.py --predictions predictions.json
```

`predictions.json` 结构：`{"ev-001": {"top3": ["hb-123"], "answer": "……", "behavior": "answer"}}`，缺项按失败计，不静默跳过。

### 检索路径对比（同一套 150 题）

```powershell
& $py scripts\build_index.py                      # 建索引（一次即可）
& $py scripts\embed_bench.py                      # 跑 bm25 / vector / hybrid
& $py scripts\embed_bench.py --pipelines hybrid+rerank,vector+rerank   # 加重排
```

| 检索路径 | Top-3 命中 | 标准问 | 同义问法 | 多轮追问 | 冲突题 | 110 题耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| BM25（二元组） | 80/110 (72.7%) | 37/45 | 25/42 | 15/20 | 3/3 | 0.2 s |
| 向量（bge-large-zh-v1.5） | 86/110 (78.2%) | 38/45 | 31/42 | 14/20 | 3/3 | 3.3 s |
| 混合（向量 + BM25，RRF） | 88/110 (80.0%) | 40/45 | 31/42 | 14/20 | 3/3 | 2.6 s |
| 向量 + 重排 | 99/110 (90.0%) | 43/45 | 35/42 | 18/20 | 3/3 | 115 s |
| **混合 + 重排** | **100/110 (90.9%)** | **45/45** | 34/42 | 18/20 | 3/3 | 119 s |

**达标（≥90%），但代价要说清楚**：重排让 110 题多花 119 秒，约 **1.1 秒/题**。NFR-01 要求复杂回答首字不超过 3 秒，这个开销能吃得下，但必须做两件事——把候选数从 20 降到 10，并把重排批量化；或者换更小的 `bge-reranker-base`。

### 调优过程中五个有数据支撑的结论

1. **查询指令前缀在这批数据上是有害的**：bge 官方建议查询加「为这个句子生成表示以用于检索相关文章：」，实测 **74.5% → 78.2%（去掉前缀反而更高）**。已把 `query_prefix` 置空，配置里留了注释。
2. **召回不是瓶颈，排序才是**：gold 在 Top-10 内占 90%、Top-20 内占 95.5%，Top-3 只有 74.5%。这正是重排能补 13 个点的原因。
3. **导语块必须排除**：「XXX管理办法 杭电教[2013]109号为规范……制定本办法」反复出现主题词却不含答案，实测「选课分几轮」直接命中导语。排除 28 个导语块后单元从 607 降到 579。
4. **两条检索路径确实互补**：两者都进 Top-3 的 68 条，只有向量进 14 条，只有 BM25 进 12 条。RRF 融合拿回其中一部分，剩下 16 条靠重排。
5. **多轮题必须带上下文**：只喂「周末也这样吗」单句，任何检索器都答不了；把上一轮问题拼进查询后，多轮题从 12/20 升到 18/20。

### 标注修正（不是为了让分数好看）

评测过程中发现 4 条 gold 标注过窄——校规与国家规定对同一问题各有一条平行条文，原标注只认校规那条：

| 题号 | 原 gold | 补充 | 理由 |
| --- | --- | --- | --- |
| ev-001 | hb-123 | + hb-009 | 新生报到，校规第三条与国家规定第八条同答 |
| ev-011 | hb-169 | + hb-031 | 退学情形，校规第四十九条与国家规定第三十条并列 |
| ev-012 | hb-177 | + hb-034 | 结业条件，校规第五十七条与国家规定第三十三条并列 |
| ev-021 | hb-279 | + hb-062 | 申诉复查期限，校规第十六条与国家规定第六十一条同为 15 日 |

修正后 BM25 也从 71.8% 升到 72.7%——**说明这不是给某一方放水**。

### 这套题还测不了什么

| 指标 | 现状 | 缺口 |
| --- | --- | --- |
| 无答案拒答率 | 基线 80%，尚未接阈值策略 | 需要置信度模块（FR-11） |
| 澄清正确率 | 0%，当前无澄清逻辑 | 需要槽位/歧义检测（FR-13） |
| 边界合规率 | 0%，当前无边界规则 | 需要答复边界规则（FR-20~24） |
| 端到端回答质量 | 未测 | 需要生成层 + `score_eval.py --predictions` |

### 题库已知局限

1. `gold` 多为单块。真实答案可能合法地引用相邻条（如“不授予学位”会牵出第二、三条），单块 gold 会让 Top-3 判定偏严。扩题时可给多块 gold。
2. 手册没有「校区」维度，所以澄清题考的是**话题歧义**而不是需求文档里的校区/身份槽位。接真实认证后要补一组带校区、身份的澄清题。
3. 学籍类占比偏高，反映的是手册篇幅分布，不是预期的线上提问分布。真实上线后应按日志分布重配权重。
4. 边界题（8 条）和无答案题（20 条）数量少，只够做冒烟；扩到 300 条时这两类应至少各 40 条。

## 还没做的（下一步）

- **表格页结构化**：创新学分认定标准、奖学金等级/金额/比例、医保报销比例，需要人工建字段（金额、比例、适用条件），不能靠切块。
- **向量化入库**：`handbook_chunks.jsonl` 是给 RAG 用的现成输入——`text` 做嵌入，`source/doc/article/page` 做引用与版本回溯。建议先按文档切 3～5 个语义段再做 embedding，单条太短的块（<80 字，现 273 块）可以并入相邻条后一起嵌入，但**引用时仍指回各自的条**。
- **题库扩到 300 条**：在 `build_eval_set.py` 的 `ROWS` 里继续追加即可，`check_eval_set.py` 会把条数上限当作硬校验；重点补多轮（现 20，应到 40）、边界（现 8，应到 40）、无答案（现 20，应到 40）。
- **办事途径信息**：承办单位、窗口、电话、服务时段、官方入口链接，手册里没有，需对接学校官网/部门确认后补进知识条目。
- **时效校验**：按文号（如 `杭电教[2013]98号`）检索是否已被新文件替代，替换后版本号加一、保留旧版本。
