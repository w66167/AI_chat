# 检索层架构

## 为什么先定架构

需求文档 NFR-08 要求「嵌入模型、向量库、大模型与知识库均可独立替换，替换不改变对外接口与数据模型」。这句话翻译成工程约束就是三条：

1. **换模型只改配置，不改调用代码**；
2. **索引是派生产物，可重建、可校验，不能手工维护**；
3. **检索、评测、生成三者互不依赖**，否则换任何一环都要动另外两环。

在这份架构之前，项目里已经埋了两个隐患，这一版一并修掉：

| 隐患 | 后果 | 处理 |
| --- | --- | --- |
| `score_eval.py` 自己实现了一套 BM25 | 基线与真实系统走两条代码路径，分数不可比 | BM25 抽到 `kb/lexical.py`，与向量检索共用同一个评测入口 |
| 索引没有指纹 | 换了模型还用旧索引，分数莫名其妙 | 索引带 `fingerprint`，不匹配直接拒绝加载 |

## 分层

```text
┌──────────────────────────────────────────────────────────┐
│ 调用方                                                    │
│   scripts/build_index.py   建索引（离线、幂等）           │
│   scripts/embed_bench.py   多模型对比 + 打分              │
│   scripts/score_eval.py    对外部系统输出打分             │
└───────────────────────────┬──────────────────────────────┘
                            │ 只依赖下面四个对象
┌───────────────────────────▼──────────────────────────────┐
│ kb/retriever.py   Retriever.search(query, k)             │
│                   → [(parent_chunk_id, score)]           │
├──────────────────────────────────────────────────────────┤
│ kb/index.py       Index.save / load / search             │
│                   numpy 矩阵 + 余弦；带指纹校验           │
├──────────────────────────────────────────────────────────┤
│ kb/embedder.py    Embedder 接口（encode 文本 → 向量）     │
│                   SentenceTransformerEmbedder 是实现之一  │
├──────────────────────────────────────────────────────────┤
│ kb/corpus.py      Unit（检索单元）与 Chunk（引用单元）    │
│                   长块拆分；子块保留 parent_id            │
└──────────────────────────────────────────────────────────┘
```

`kb/config.py` 是所有可调参数的唯一入口（`config.json`），任何模块不写死模型名、阈值、路径。

## 检索路径（实测可切换）

`kb/hybrid.py` 提供两条可组合路径，`scripts/embed_bench.py` 用同一套题库给它们打分：

```text
bm25                    ▸ 纯关键词，0.2 秒，72.7%
vector                  ▸ bge 嵌入 + 余弦，3.3 秒，78.2%
hybrid                  ▸ vector ⊕ bm25（RRF 融合），2.6 秒，80.0%
vector+rerank           ▸ 向量取 20 候选 → 交叉编码器重排，115 秒，90.0%
hybrid+rerank           ▸ 融合后重排，119 秒，90.9%   ← 当前默认路线
```

配置里 `retrieval.mode` 与 `reranker.enabled` 决定走哪条，代码不用改。重排的开销是每条约 1.1 秒，上线前要么把候选数降到 10，要么换 `bge-reranker-base`。

## 五个关键设计决定

### 1. 检索单元 ≠ 引用单元

bge-large-zh-v1.5 最多 512 token，而语料里有 3 块超过 900 字、几十块在 500 字以上。直接截断等于尾部条文永远检索不到。

所以拆成两层：

- **Unit**：真正送去嵌入的文本片段，长度受 `max_chars` 约束；
- **Chunk**：用户看到的引用单元，仍是原来那一整条，带文件、条号、页码。

子块 id 形如 `hb-216#2`，检索命中后按 `parent_id` 归并，**引用永远指回整条**。这样既不丢内容，也不破坏「答案可追溯到唯一某条」的验收要求。

### 2. 索引指纹

```python
fingerprint = sha1(model_id | dim | corpus_version | max_chars | overlap | normalize)
```

加载索引时比对指纹，不一致就报错退出，而不是拿旧索引打出好看但错误的分数。`data/indexes/` 全部是派生产物，删掉重跑即可。

### 3. Embedder 是接口

```python
class Embedder(Protocol):
    name: str
    dim: int
    def encode(self, texts: Sequence[str], is_query: bool) -> np.ndarray: ...
```

`is_query=True` 时才加查询指令前缀（bge 的「为这个句子生成表示以用于检索相关文章：」）。文档侧不加前缀——这个细节写错会让分数凭空掉几个点，所以放在接口语义里而不是调用处。

换模型 = 改 `config.json` 里 `embedder.active`。BM25 不走嵌入，因此它实现的是上一层的 `Retriever` 接口（`kb/lexical.py`），与向量检索并列。**两者接口相同，所以同一个 `metrics.topk_hit` 能直接给它们打分**，分数可比。

### 4. 检索不依赖评测

`Retriever.search` 只做检索。评测集只在 `kb/metrics.py` 里被读取，不会进入运行时。将来把检索层接到小程序或 API 时，只搬 `kb/` 和索引文件，不搬题库。

### 5. 运行时契约

对上层（小程序、后端 API）只暴露一个形状：

```python
{"chunk_id": "hb-216", "score": 0.83, "text": "……", "source": "《…》第三条 第70页"}
```

生成层（大模型）只消费这个结构，不关心向量怎么算。将来换 LLM 或换模型，这一层契约不变。

## 当前不做的事（以及为什么）

| 不做 | 原因 |
| --- | --- |
| FAISS / Milvus / Qdrant | 586 条 × 1024 维 = 2.4 MB，`numpy` 矩阵乘法毫秒级；上向量库只增运维成本 |
| 微调嵌入模型 | 30 条问答、150 条评测，量级远不够微调；先用量化好的现成模型 |
| 自建分词 + 倒排 | BM25 用二元组已够做基线对照，中文分词器会把「校园卡」切成「校园/卡」反而更差 |
| GPU 常驻服务 | 建索引是一次性离线任务，查询是嵌入单条句子，脚本级调用足够；上线再做服务化 |
